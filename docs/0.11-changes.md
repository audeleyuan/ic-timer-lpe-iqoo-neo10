# 0.11.0 变更说明

## 1. 目标门：vivo/iQOO + 6.1.145

旧版 `ic-timer slide` 只认 `gf506252fa70d`。0.11 把门拆成三层：

| 层 | 检查 | 位置 |
|---|---|---|
| shell 预检 | `uname -r` 含 `6.1.145`；`getprop` 的 manufacturer/brand/model/device 含 vivo/iqoo 或以 V2/PD2/PD3 开头 | `run_lpe.sh` / `device/run.sh` |
| 二进制内核门 | `osrelease` 含 `6.1.145` | `ic_slide_mode` |
| 设备门 | 读 `/system/build.prop` 等文件的 `ro.product.*`；shell 通过后导出 `IC_DEVICE_VIVO=1` 直接放行 | `ic_device_is_vivo` |

测试开关：`IC_ALLOW_ANY_KERNEL=1`（shell）、`IC_DEVICE_ANY=1`（二进制/
QEMU）、`IC_SLIDE_ANY=1`（跳过全部检查）。

## 2. 新 build 的符号表

### 为什么需要

slide 的投票是 `slide = raw - (link(name) + off)`，`link(name)` 是**链接期**
地址；mcast 链还要 `__tracepoint_sys_exit`、`selinux_state`、`init_user_ns`、
`init_cred` 的链接期地址。内核 minor 相同但链接顺序/配置不同的 build，地址
完全不同（实测同是 6.1.145：`__tracepoint_sys_exit` 从
`0xffffffc00a2d1860` 变成 `0xffffffc00a3cb180`）。

### 运行期

- 先按 `uname -r` 匹配二进制内置的 per-build 表：Y500/PD2506/V2506A (`gf506252fa70d` 与 `g3de37d73fd1d`)、
  iQOO 12/PD2307/PD2329 (16.2.20.3 与 16.2.20.7，内核相同) 和 X100 Pro/X100s Pro (PD2324/V2324A/V2324HA, 16.2.12.0 与 16.2.13.1 两版) (`maybe-dirty`)。注意 PD2324 与
  iQOO 12 的 `uname -r` 完全相同但 66 个地址全不同；选择已知表时核对
  机型 (PD2506 / V2506 / PD2307 / PD2329 / V2307 / PD2324 / V2324A / V2324HA)。匹配到就直接用，**不需要任何文件**。
- 未匹配的 build 才读 `IC_SYMS_FILE`（默认
  `/data/local/tmp/ic-syms.txt`）；表头 `build=` 必须与 `uname -r`
  相同（允许一方包含另一方），否则拒绝。
- **具体版本检测**：内置表要求 `uname -r` + 机型 + `ro.build.display.id`
  三项同时匹配（例如 `PD2307_A_16.2.20.3.W10.V000L1`）。shell 导出
  `IC_DEVICE_MODEL` / `IC_BUILD_VERSION`，二进制也读 build.prop。任一项
  不一致就不使用内置表，回退到 `/data/local/tmp/ic-syms.txt` / 解析；
  这也是 PD2324 与 iQOO 12 同 `uname` 但不会串表的保险。
- 外部表/表文件兼容 CRLF；`ic_syms_load_file` 会剥掉行尾 ``，避免 Windows 生成的表 build 头匹配失败。
- 外部表也缺失时只有 gf506252 能继续；其他 build 打印：
  `ic-timer syms <boot.img> /data/local/tmp/ic-syms.txt`（App 的
  “解析偏移”会打开系统文件选择器）。

### 解析器（`ic_syms.c`）

输入：Android boot v0–v4（`ANDROID!`，kernel 在 header 页之后）、原始
ARM64 Image、lz4-legacy/gzip/zlib 压缩内核、vmlinux ELF（.symtab）、
System.map/ksyms.txt 文本。

ARM64 Image 路径是 `kallsyms_py.py` 的 C 移植：

1. 找 `0\0 1\0 … 9\0` token 表头，校验 256 个 token 与 u16 索引；
2. 在 token 表前 4 MB 找 marker 表（首个 u32=0，后续差分 0x200..0x40000）；
3. 从 `names_offset ≈ markers_offset - last_marker` 回溯最多 0x40000 找
   `num_syms`、压缩名流（ULEB 或 raw length）；
4. 解码 11 万个名字，要求 `_text`/`_end`/`load_module` 存在；
5. 用 `_text`/`_end`、地址单调、90% 落在镜像内三条规则验证地址表
   （pre-6.4 与 6.4+ 两种布局都试）。

输出 66 行 `name=0xaddr` + 表头 `# build=`。

## 3. KSU 交接（`ksu_handoff.sh`）

按 X300/t61269 的流程重写：

1. **KMI**：空参时由 `uname -r` 推导（6.1.* → `android14-6.1`）。
2. **每次重新提取 ksud**：不再优先 `/data/adb/ksu/bin/ksud`（可能是旧
   manager 留下的）；从 `pm path` 的 APK 目录 `lib/arm64/` 逐个复制
   >1 MB 的 `.so`，执行 `--version` 和 `late-load --help`，命中
   `uapi`/`late-load`/`--kmi` 的才优先；`libksud.so` 是最后兜底；
   APK 内嵌（没有抽取目录）时用 `unzip -p`。
3. **逐个管理器尝试**：显式选择的包优先，然后按 KNOWN 列表把所有已安装
   管理器都试一遍（7kimisu 的内核只认自己的签名，一次选择错误不再直接
   失败）。`me.inkdye.vivoksu`、`com.rifsxd.ksunext`、`me.yuki.fina` 也
   加入列表。
4. **late-load 形式**：`--allow-shell --kmi <kmi> --package-name <pkg>` →
   去掉 `--kmi` → 去掉 `--package-name` → 只 `--allow-shell`。
5. **成功判定不依赖 `/proc/modules`**：模块名不统一且有些 fork 会隐藏；
   `/sys/module/{kernelsu,ksu}`、`/proc/modules` 行、`su -c id` 任一成立
   即算 live。每次 late-load 后轮询 20 s。
6. live 后执行 `ksud install`（180 s），再轮询 su 30 s，然后
   `am force-stop` + `monkey` 拉起管理器，让「越狱模式」页补用户态。
7. 所有管理器都失败时，才退回已安装的 `/data/adb/ksu/bin/ksud`（并在日志
   中说明不是新提取的）。
8. 退出码：0 = 模块 + su；6 = live 但 su 不可用；7 = 未确认。

## 4. 安全模式

- `ksu_handoff.sh` 的第 3 个参数（或 `IC_SAFE_MODE=1`）为 1 时，在
  late-load **之前**给 `/data/adb/modules/*` 和 `modules_update/*` 写
  `disable`。KernelSU 模块加载逻辑会跳过带该文件
  的目录（ksud 字符串里有 `is disabled, skip` / `Failed to remove
  disable file`）。
- 已禁用的模块不重复记录；路径写进
  `/data/adb/ksu/ic-disabled-modules.txt`。
- `safemode.sh --restore` / `cleanup.sh --restore-modules` 只恢复本工具
  记录的那些，不会重新启用用户自己禁用的模块。
- 未使用 `ksud safemode`/`persist.sys.safemode`：各 fork 的 CLI/属性语义
  不一致，`disable` 文件是所有 KernelSU/Magisk 兼容实现共同认的机制。

## 5. 清理

`cleanup.sh` 默认只删 KSU 相关目录 + 本工具临时文件；`--apk` 才卸载管理器。
不碰 `/data/adb/magisk`、`post-fs-data.d`、`service.d`。内核模块要重启消失。

## 6. 关闭 USB 调试不再重启

症状：提权后关闭 USB 调试，手机重启。原因链：

1. 关闭 USB 调试 → adbd 停止 → 以 ADB 启动的 Shizuku 服务/用户服务被杀；
2. 服务的 stdout/stderr 管道被关闭；
3. parked attempt（以及正在跑的 mcast winner）下一次 `write(2)` 得到
   SIGPIPE，默认动作是杀进程；
4. 被杀的 attempt 释放了被改写的 timer 节点 →
   `posix_cpu_timers_exit → timerqueue_del/rb_next` oops →
   `panic_on_oops=1` 重启。

修复：

- `timer_lpe.c` 加了一个永久的 constructor
  `ic_ignore_sigpipe()`，整个进程树（fork/exec 后仍继承 SIG_IGN）忽略
  SIGPIPE；日志管道断掉只得到 EPIPE。
- `run_lpe.sh` / `run.sh` 都 `trap '' PIPE HUP INT TERM`。
- `IcService.start` 用 `/system/bin/setsid sh <script>` 启动整条链，
  把计划放进独立 session；关闭 USB 调试时 adbd 的进程组 kill 够不到
  parked attempts。设备端 `run.sh` 也先 `setsid` 再 exec。
- 这些改动不改变 exploit 的地址/尝试逻辑，只改变存活方式。
